# PlayAPI user accounts, Steam login, wishlists, and custom lists

## Summary

Add a user-owned feature domain alongside the existing IGDB catalog domain.

- CatalogAPI remains read-only and serves IGDB/Steam catalog data.
- PlayAPI owns authentication, users, lists, wishlist membership, visibility, and history.
- User data lives in a separate `playdb` database on the same PostgreSQL server.
- Mobile authentication uses Steam OpenID in the system browser and returns to Expo through a deep link.
- Steam OpenID provides the SteamID; PlayAPI uses the Steam Web API to enrich the profile with persona name and avatar data.
- Use `AspNet.Security.OpenId.Steam` for the ASP.NET Core Steam/OpenID provider.

## Database and migrations

Use code-first EF Core migrations for PlayAPI. Do not add PlayAPI tables to the catalog grate migrations.

```text
code/app/backend/PlayAPI/
└── Infrastructure/Persistence/
    ├── PlayDbContext.cs
    ├── PlayDbContextFactory.cs
    └── Migrations/
        ├── <timestamp>_InitialPlaySchema.cs
        └── PlayDbContextModelSnapshot.cs
```

The catalog remains database-first and grate-managed. PlayAPI owns its user schema, entities, configuration, and migration history.

PlayAPI should reference `Microsoft.EntityFrameworkCore` and `Microsoft.EntityFrameworkCore.Design` privately, and the repository's `dotnet-ef` tool version should match the central EF Core package version. The design-time factory supplies the `playdb` connection for migration commands without requiring the running API. The AppHost should reference `Aspire.Hosting.EntityFrameworkCore` for migration orchestration.

The `playdb` schema contains:

- `users`: internal UUID, unique SteamID, persona name, avatar URLs, role, and timestamps.
- `lists`: owner, name, description, private/public visibility, default flag, and timestamps.
- `list_items`: list ID, IGDB game ID, actor, timestamp, and unique `(list_id, game_id)`.
- `list_history`: list ID, game ID, actor, added/removed action, and timestamp.
- `auth_sessions`: hashed opaque bearer token, user ID, expiry, revocation, and client metadata.
- `auth_transactions`: hashed one-time exchange code, OpenID state/nonce, expiry, consumed timestamp, and redirect state.

Because `playdb` is separate from `catalogdb`, list tables store IGDB IDs without database-level foreign keys to catalog games. Clients compose list membership with CatalogAPI game queries.

The default `Wishlist` is created transactionally during first-user provisioning. It cannot be renamed or deleted, but its visibility and contents can be changed.

Update the catalog orchestration to:

- add a `play-database` parameter;
- run catalog migrations against `catalogdb`;
- run the PlayAPI EF migration bundle against `playdb`;
- pass `ConnectionStrings__playdb` to PlayAPI;
- keep both databases on the same PostgreSQL host and credentials.

PlayAPI must not mutate production implicitly during application startup. Developers create migrations manually when the model changes. Aspire local run mode applies pending migrations through `RunDatabaseUpdateOnStart()`. Aspire publish generates the migration bundle for deployment.

```powershell
dotnet ef migrations add InitialPlaySchema --project PlayAPI --startup-project PlayAPI
```

The `migrations add` command is only run when the PlayAPI EF model changes. The generated migration files are committed. The migration bundle is generated by Aspire through `PublishAsMigrationBundle`; its connection string is injected by Aspire/Dokploy and never committed.

## PlayAPI authentication

Add Steam OpenID authentication to PlayAPI.

### Login flow

1. Expo generates a local `state` and opens the PlayAPI Steam login URL using the system browser/AuthSession.
2. PlayAPI creates an expiring authentication transaction and redirects to Steam.
3. Steam redirects to the fixed PlayAPI callback.
4. PlayAPI validates the OpenID response and extracts the SteamID.
5. PlayAPI calls the Steam Web API with a server-only API key for profile data.
6. PlayAPI upserts the user and creates the protected default Wishlist if needed.
7. PlayAPI creates a short-lived, one-time exchange code.
8. PlayAPI redirects to `gameindex://auth/callback?code=...&state=...`.
9. Expo exchanges the code through PlayAPI.
10. PlayAPI returns an opaque bearer access token and current user profile.
11. Expo stores the token in secure storage and sends it using the `Authorization` header.

The exchange code is single-use and stored hashed. Bearer sessions are also stored hashed in `auth_sessions` and can be revoked on logout.

### Claims

- `sub`: internal user UUID
- `steam_id`
- `name`
- `avatar`
- `role=user`

Only the `user` role is implemented. Mutations require authentication and the user role. Public list reads do not require authentication.

### Authentication endpoints

```text
GET  /auth/steam/login
GET  /auth/steam/callback
POST /auth/mobile/exchange
POST /auth/logout
GET  /auth/me
```

`/auth/me` returns the current user and default Wishlist metadata.

## List API

Owner routes are under `/api/me`:

```text
GET    /api/me/lists
POST   /api/me/lists
GET    /api/me/lists/{listId}
PATCH  /api/me/lists/{listId}
DELETE /api/me/lists/{listId}

PUT    /api/me/lists/{listId}/games/{gameId}
DELETE /api/me/lists/{listId}/games/{gameId}

GET    /api/me/lists/{listId}/history

GET    /api/me/wishlist
PUT    /api/me/wishlist/games/{gameId}
DELETE /api/me/wishlist/games/{gameId}
```

Public access:

```text
GET /api/lists/{listId}
```

Rules:

- public lists are readable anonymously;
- private lists return `404` to non-owners;
- only owners can edit, delete, or change visibility;
- public responses expose list metadata, current game IDs, and timestamps;
- history is owner-only;
- adding an existing game is idempotent;
- removing a missing game is idempotent;
- membership changes append history in the same transaction;
- list names and descriptions are length-validated;
- the protected Wishlist cannot be renamed or deleted.

Use a manually maintained `PlayDbContext` and entity configuration in PlayAPI. EF migrations own the PlayAPI schema; PlayAPI must not call `EnsureCreated` or run `Database.Migrate()` implicitly during normal application startup.

### Persistence contracts

```csharp
public sealed class PlayDbContext(DbContextOptions<PlayDbContext> options) : DbContext(options)
{
    public DbSet<User> Users => Set<User>();
    public DbSet<UserList> Lists => Set<UserList>();
    public DbSet<ListItem> ListItems => Set<ListItem>();
    public DbSet<ListHistoryEntry> ListHistory => Set<ListHistoryEntry>();
    public DbSet<AuthSession> AuthSessions => Set<AuthSession>();
    public DbSet<AuthTransaction> AuthTransactions => Set<AuthTransaction>();
}

public sealed class User
{
    public Guid Id { get; set; }
    public long SteamId { get; set; }
    public string SteamName { get; set; } = string.Empty;
    public string? AvatarSmallUrl { get; set; }
    public string? AvatarMediumUrl { get; set; }
    public string? AvatarFullUrl { get; set; }
    public string Role { get; set; } = "user";
    public DateTimeOffset CreatedAt { get; set; }
    public DateTimeOffset UpdatedAt { get; set; }
}

public sealed class UserList
{
    public Guid Id { get; set; }
    public Guid OwnerId { get; set; }
    public string Name { get; set; } = string.Empty;
    public string? Description { get; set; }
    public ListVisibility Visibility { get; set; }
    public bool IsDefault { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public DateTimeOffset UpdatedAt { get; set; }
}

public sealed class ListItem
{
    public Guid ListId { get; set; }
    public long GameId { get; set; }
    public Guid AddedByUserId { get; set; }
    public DateTimeOffset AddedAt { get; set; }
}

public enum ListVisibility
{
    Private,
    Public
}
```

`OnModelCreating` must define the PlayAPI schema: snake_case names, enum conversion, unique SteamID, unique list membership, indexes for owner/visibility, and no catalog-game foreign key. EF generates the migration from this model.

### Authentication contracts

```csharp
public interface ISteamProfileClient
{
    Task<SteamProfile> GetProfileAsync(long steamId, CancellationToken ct);
}

public interface IUserProvisioningService
{
    Task<User> ProvisionAsync(SteamProfile profile, CancellationToken ct);
}

public interface IAuthSessionService
{
    Task<string> CreateSessionAsync(User user, string? client, CancellationToken ct);
    Task<Guid> ConsumeMobileExchangeAsync(string code, CancellationToken ct);
    Task RevokeAsync(Guid userId, string token, CancellationToken ct);
}

public sealed record SteamProfile(
    long SteamId,
    string Name,
    string? AvatarSmallUrl,
    string? AvatarMediumUrl,
    string? AvatarFullUrl);
```

The Steam provider callback should call `IUserProvisioningService`, then `IAuthSessionService`, and redirect only with a one-time code. It must never put a bearer token in the redirect URL.

The bearer authentication handler hashes the incoming token, looks up `AuthSessions`, rejects expired/revoked rows, and creates a `ClaimsPrincipal` with `sub`, `steam_id`, `name`, `avatar`, and `role` claims.

### PlayAPI registration shape

```csharp
builder.Services.AddDbContext<PlayDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("playdb"))
        .UseSnakeCaseNamingConvention());

builder.Services
    .AddAuthentication("PlayBearer")
    .AddScheme<AuthenticationSchemeOptions, PlayBearerHandler>("PlayBearer", null);

builder.Services.AddAuthorizationBuilder()
    .AddPolicy("User", policy =>
        policy.RequireAuthenticatedUser().RequireRole("user"));

builder.Services.AddSteam(options =>
{
    options.ApplicationKey = builder.Configuration["Steam:ApplicationKey"]!;
    options.CallbackPath = "/auth/steam/callback";
});
```

The exact provider option names must be confirmed against the installed package version before implementation. Secrets come from Aspire/Dokploy configuration, never source control.

The service owns authorization and transaction boundaries. Endpoints should not directly manipulate `PlayDbContext`.

### Endpoint shape

```csharp
public static async Task<Results<Ok<ListDetails>, NotFound, ValidationProblem>> HandleAsync(
    Guid listId,
    UpdateListRequest request,
    ClaimsPrincipal principal,
    IListService lists,
    CancellationToken ct)
{
    var userId = principal.GetRequiredUserId();
    var result = await lists.UpdateAsync(userId, listId, request, ct);
    return result is null ? TypedResults.NotFound() : TypedResults.Ok(result);
}
```

Each feature slice should contain its request/response types, endpoint, validator, and mapping code. `Map.cs` only maps routes, attaches authorization policies, and declares OpenAPI responses.

### Transaction shape for membership changes

```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);

var item = await db.ListItems.FindAsync([listId, gameId], ct);

if (item is null)
{
    db.ListItems.Add(new ListItem { ... });
    db.ListHistory.Add(new ListHistoryEntry { Action = ListAction.Added, ... });
}

await db.SaveChangesAsync(ct);
await transaction.CommitAsync(ct);
```

The remove path deletes the active membership and records a `removed` history event. Repeated add/remove requests remain idempotent.

## Mobile client integration

After PlayAPI OpenAPI is exposed:

- regenerate the mobile client with `pnpm run generate`;
- add `mobile/src/features/auth`;
- open Steam login through Expo browser/AuthSession support;
- handle `gameindex://auth/callback`;
- exchange the one-time code;
- persist the bearer token using secure storage;
- add shared authenticated request configuration for generated PlayAPI hooks;
- add list screens and mutations under `mobile/src/features/lists`;
- compose game metadata from CatalogAPI using stored IGDB IDs;
- invalidate list queries after mutations.

### Mobile authentication shape

```ts
const result = await WebBrowser.openAuthSessionAsync(
    `${apiUrl}/auth/steam/login?state=${state}`,
    'gameindex://auth/callback',
)

if (result.type === 'success') {
    const { code, state: returnedState } = parseCallback(result.url)
    const session = await exchangeMobileCode({ code, state: returnedState })
    await SecureStore.setItemAsync('playapi.access_token', session.accessToken)
}
```

Generated PlayAPI hooks should receive the token through the shared request/auth configuration. Auth state belongs to a small auth store; list state belongs to TanStack Query and is invalidated after mutations.

### Orchestration shape

The user-facing AppHost should add PlayAPI and its migration resource using the PlayAPI connection string:

```csharp
var playDb = builder.AddConnectionString("playdb");

var playApi = builder
    .AddProject("playApi", "./../app/backend/PlayAPI")
    .WithReference(playDb)
    .WithEnvironment("Steam__ApiKey", steamApiKey)
    .WithHttpsEndpoint();

var playMigrations = playApi
    .AddEFMigrations("playapi-migrations")
    .RunDatabaseUpdateOnStart()
    .PublishAsMigrationBundle(publishContainer: true);

playApi.WaitForCompletion(playMigrations);
```

The migration resource must complete before PlayAPI starts. CatalogAPI continues to wait only for catalog migrations. The catalog pipeline remains grate-based; the PlayAPI database is managed through Aspire EF migrations. For Docker Compose publishing, configure the migration service with `Restart = "no"` because it is a one-shot resource.

No user data is added to the IGDB pipeline or CatalogAPI schema.

## Future Steam wishlist metrics

Steam's aggregate wishlist count is catalog data, not user-list data.

```text
catalogdb
└── Steam aggregate wishlist counts

playdb
└── User list memberships
```

A future pipeline feature can ingest Steam wishlist counts into `steam_raw`, transform them into a current/latest mart, and expose them through CatalogAPI without changing PlayAPI's schema or private user data.

## Test plan

### Migration tests

- Run PlayAPI EF migrations against a PostgreSQL test container.
- Verify tables, enums, unique constraints, and indexes.
- Verify migration idempotency.
- Verify default Wishlist protection and list-item uniqueness.
- Verify the same PostgreSQL server can migrate `catalogdb` and `playdb` independently.
- Verify a fresh PlayAPI database can be created entirely from the EF migration bundle.

### Authentication tests

- Invalid Steam OpenID responses are rejected.
- Expired or mismatched state is rejected.
- First login creates exactly one user and Wishlist.
- Repeated login does not duplicate either record.
- Exchange codes are single-use and expire.
- Revoked or expired bearer sessions are rejected.
- Claims contain the internal ID, SteamID, and user role.

### List tests

- Authenticated users can create, update, and delete normal lists.
- Wishlist cannot be renamed or deleted.
- Add/remove operations are idempotent.
- Duplicate memberships are prevented.
- Membership history records actor, game, action, and timestamp.
- Owners can read private lists.
- Non-owners cannot read private lists or mutate public lists.
- Anyone can read public lists.
- Invalid IDs, names, descriptions, and visibility values return validation problems.

### API/client tests

- Generate the PlayAPI Kiota client from OpenAPI.
- Exercise REST endpoints through generated request builders and models.
- Do not hand-build route strings in tests.
- Keep real Steam-provider testing as a manual environment test.
- Use a test authentication scheme for list endpoint tests; do not call Steam in automated tests.
- Use generated PlayAPI request builders and models in integration tests.

## Assumptions

- Mobile is the first client; web can reuse the same endpoints later.
- Mobile callback scheme is `gameindex://auth/callback`.
- PlayAPI uses opaque bearer sessions rather than ASP.NET Identity or JWT.
- Only one role exists: `user`.
- Lists reference IGDB game IDs and do not duplicate catalog metadata.
- History records membership events, not full snapshots.
- The default Wishlist is protected from rename/delete but can be public.
- The Steam Web API key is server-only and supplied through Aspire/Dokploy configuration.
- Steam aggregate wishlist counts remain pipeline/CatalogAPI data and are never mixed with user Wishlist membership.
